# Claude 主控 · Codex 辅助（2026-10-24 起）

用户定的分工：**Claude 是主力，Codex 是助手。** 繁杂、耗时的活（整理史书、考证、建档、生图、批量处理）交给 Codex；
大纲、旁白、分镜、引擎代码、验收和与用户沟通归 Claude。Claude 直接用命令行给 Codex 派活，用户不再中转任务单。

## 一、谁做什么

| 归 Claude | 归 Codex |
|---|---|
| 选题、主问题、大纲、钩子、旁白（narration skill） | **史料包**：事件表、原文摘句、出处段落 ID、纪传互见、演义对照、争议 |
| 分镜、episode.yaml、镜头、动作编排（storyboard skill） | 人物档案：生卒、本集年龄、官职；人物相貌档案 + 立绘（history-portrait skill） |
| 引擎：studio.py、territory.py、remotion-shuihong/src | 地点考证：古今对照、谭图坐标、城邑等级（提案或直接写 gazetteer，见第四节） |
| 构建、预览、成片自检、发布包 | 情景插画、动画素材、图标的研究与生图 |
| **验收 Codex 的交付**，并决定用不用 | 读音核查（多音字、生僻字 → 读音.yaml 提案）、疆域事件的史料核对 |
| 和用户沟通，最终方案的取舍 | 批量机械活：抠图、对照图、清单、格式整理；成片的第二遍史实审读 |

判断标准：要**品味和全局判断**的归 Claude；要**翻书、查证、反复生成**的归 Codex。拿不准时，Codex 只出材料和建议，由 Claude 定。

## 二、单集流水线里的派活点

```
（提前 1–2 集）Codex：史料包 ──► Claude：主问题 + 大纲 + 旁白（抽查史料包原文）
                                          │ 旁白定稿
              ┌───────────────┬───────────┴──────┬────────────────┐
        Codex：新地点考证  Codex：人物/立绘  Codex：插画需求→生图  Codex：读音核查
              └───────────────┴───────────┬──────┴────────────────┘
                     Claude：分镜、构建、预览（素材到了就接，不等齐）
                                          │
                     Codex：成片史实第二遍审读（可选） ──► Claude 汇总 ──► 用户预览
```

- **史料包要提前跑**：做第 N 集时，就把第 N+1、N+2 集的史料包派出去。Claude 写大纲时史料已经齐了，不用干等。
- **旁白定稿后再派素材活**：立绘名单、插画场景、读音核查都依赖定稿的台词；台词还在改时派，会白做。
- **构建不等素材**：先用旧图和占位排版，Codex 交付一件接一件。

### 原文一律结构化，交给脚本核对

凡是 Codex 交来的原文（史料包、审读、相貌档案的 recorded 等），每条都要写成 `{quote: 原文, para: 段落ID}`。段落 ID 就是 `studio.py sources` 搜出来的 `id`，例如 `三国志-p01189`。本地语料里没有的原文（比如维基文库上的注文），写成 `{quote: …, url: …, para: 无}`。
Claude 验收时，先跑一遍：

```powershell
python tools/verify_quotes.py <文件>
```

脚本会逐字核对每一条原文。它报「查无此文」的条目，一律打回；报「段落号错」的，照脚本给出的正确段落号改掉即可。这样能全量核对，不用再靠人工抽查。

### 战事账（有行军的集必做，2026-10-25）

和史料包一起派。产出 `06_报告/战事账/第N集-战事.yaml`，Claude 验收后复制到 `projects/<id>/战事.yaml`。`studio.py check/build` 拿它对照疆域和行军，漏了就报错（`campaign.py`）。
格式和要求见 `00_管理/codex任务/任务单-第27集战事账.md`：
- 部队表；
- 按时间排的事件，kind 只能是 出发/行军/屯驻/途经/翻越/交战/攻占/投降/退守/撤退/会合；
- `via` 写途经的关隘山岭；
- 攻占、投降写 `territory: {jun, to}`；
- 新地名写 `places_new`，附坐标依据；
- 拿不准的写 `open_questions`。

### 史料包的固定格式

存到 `01_工作流/projects/<id>/research/史料包.yaml`（YAML 方便脚本核对；另附一份 `史料包.md` 给人看，可选）。任务单里写明这些部分：
1. 事件表：时间（公元 + 年号）、人物、地点、发生了什么、原文摘句、出处（`studio.py sources` 段落 ID + 卷次）。每件事至少两处出处，查不到第二处的写明。
2. 人物：本集出场者的生卒、本集时的年龄（写算法）、官职；有无立绘、立绘是否需要重画。
3. 地点：古名、今址、gazetteer 里有没有、有的话等级对不对。
4. 演义与正史的差别；史家有争议的地方。
5. 读音风险字（人名地名的多音字、生僻字）及依据。
6. 适合做插画或战术图的场面（只列场面和史料，不写画法）。

## 三、怎么派活

一律用派活脚本，不要手敲 `codex exec`：

```powershell
python tools/codex_task.py start <名字> --brief <任务单.md> --write <允许写的目录或文件…> [--effort low|medium|high]
python tools/codex_task.py resume <名字> "具体哪里不对、怎么改"
python tools/codex_task.py status
```

- `start` 和 `resume` 会一直运行到 Codex 做完，长任务要用后台方式跑。完成后系统会通知 Claude，不需要轮询。
- 每个任务的完整记录都在 `00_管理/codex任务/<日期>-<名字>/`：任务单原文、Codex 汇报、事件流、改动文件清单、用量。这些是审计记录，不要删。
- 模型默认 `gpt-6.1-terra`（2026-10-29 用户指定，速度快；之前为省额度用 `gpt-6-luna`）。推理强度按活的性质选：
  - 机械活用 `low`；
  - 一般整理用 `medium`（默认）；
  - 需要判断的研究用 `high`，比如史料取舍、城邑分级、相貌设计。
- 脚本会在任务单后面自动附上通用纪律：只写允许的范围、不碰引擎和 beats、不渲染不提交、读写中文用 Python、查不到的史料写「未核」、最后一条消息就是汇报。所以任务单里不用重复这些。

### 审读的固定格式（成片第二遍史实审读）

存到 `06_报告/史实审读/第N-M集-审读.yaml`，格式如下：

```yaml
episodes:
  - ep: 18
    checked: 全部            # 或列出看过的拍号
    findings:
      - beat: 7              # episode.yaml 里 beats 的序号，从 1 数
        kind: 史实            # 史实 / 主语 / 箭头 / 疆域 / 读音 / 地点 / 人物 / 演义 / 缺口
        severity: 错          # 错（必须改）/ 疑（史料有分歧或拿不准）/ 建议
        problem: 一句话说清哪里不对
        evidence:
          - {quote: 原文, para: 三国志-p01189}
        suggest: 怎么改（只是建议，Claude 决定改不改）
```

Codex 只挑错，不改 episode.yaml。Claude 逐条判断：认同的自己改，拿不准的问用户。

**第 18–23 集首次审读的教训（2026-10-24）**：共报 7 条，原文全部属实，但 2 条「错」都是误报，原因是 Codex 只看了单集、不了解系列的写法。以后的审读任务单必须给出下面这些背景：
- 冷开场常常先说结局（「他死在了定军山」），地图停在故事开始的年份是有意的；每拍的 `map:` 必须按时间单调前进，不能为了冷开场往后跳。
- 跨集连续：本集结尾没画的疆域变化，可能留给下一集开场讲。要对照下一集的开头，并跑 `python consistency.py --series s01e`。
- 读音要看 `voice/asr-report.md` 的差异列（比如「叡」→「芳」、「沔」→「安」），只看读音表查不出配音实际读错的字。

**补上背景后的第 24–29 集（同日）**：报 9 条，没有误报。采纳 5 条：杨仪回成都的箭头、邓艾改从狄道出兵、两句台词、曹叡的读音；2 条读音留给用户听；2 条属于可改可不改。说明任务单里的「系列写法」背景是有效的，以后审读都照这份任务单写。

### 任务单怎么写

任务单只写**目标、背景、硬约束和验收**，研究、取舍和设计都留给 Codex（见记忆 codex-tasks-goal-based）。固定结构如下：

```
任务：一句话说清要达到什么效果（观众/用户视角）
背景：为什么要做，现在差在哪
先读：文件路径清单
你来决定的事：……（并请它对规范、工具提修改建议）
约束：范围、规格、额度（每项最多几次生图）、不能碰的东西
交付与验收：逐条可检查的产物和标准
```

## 四、不打架

- **同一目录或文件同一时间只派一个任务。** 脚本会拒绝和正在运行的任务范围重叠的派活。
- **用户自己在桌面版跑的 Codex 任务，脚本看不到**：用户告诉 Claude 正在跑哪一批，Claude 就避开那批的目录。`changes.txt` 里的「范围外」改动可能来自用户那边，要先核对是谁改的，再下结论。
- **共享登记表**（`gazetteer.json`、`读音.yaml`、`人物相貌.yaml`、`疆域.yaml`、`人物声音.yaml`）：只有任务单把它列进 `--write` 时，Codex 才能改，而且同一时间只能有一个任务在改。拿不准的条目，写成 `提案-*.yaml` 放在任务目录里，由 Claude 合并。
- Claude 不会在 Codex 运行期间去改它范围内的文件。

## 五、验收（Claude 必做，不能只看汇报）

1. 对照任务单的「交付与验收」逐条检查，文件要真的存在、内容要对。
2. 看 `changes.txt`：有范围外的改动，先查清是谁改的。Codex 越界改的，要退回或还原。
3. **史料核对**：跑 `python tools/verify_quotes.py`，全量逐字核对。只要有一条「查无此文」，就打回。`para: 无`（本地语料没有）的条目，人工抽查其中 2 条，去维基文库核对。
4. **图片**：
   - 立绘用 `portrait_faces.py` 看脸部对照；图标和插画按实际显示大小放到真实画面里看。
   - 检查透明底：四角的 alpha 值应为 0，而且没有画成假棋盘格（命令行生图的老毛病）。
5. 不合格就用 `resume` 打回，写清哪条不对、怎么改。最多打回 2 轮，还不行就停下来告诉用户，说明原因。
6. 合格后由 Claude 接进工程，并向用户汇报：做了什么、用了多少额度、还有什么没做。

## 六、已知的坑

- **Windows PowerShell 5.1 会把 UTF-8 中文读成乱码**：2026-10-24 试跑时，Codex 因此把统计做错了。派活脚本已经要求它一律用 Python 读写文件，并设置了 `PYTHONUTF8=1`。
- **Codex 的 Windows 沙箱跑不了用户目录下的 Python**：报错是拒绝访问，而 `studio.py` 必须用 Python。所以脚本是不带沙箱运行 Codex 的，越界改动靠提示词约束加事后的 `changes.txt` / git 检查。
- **命令行生图会把「透明背景」画成棋盘格**：第 6 批出过这个问题，见 HANDOFF。验收时必须查 alpha 值。
- 推理强度 `high` 的单次用量大约是 `low` 的几倍；纯格式活不要用 `high`。
